## 一、什么是向量数据库

向量数据库是专门用于存储、索引和检索高维向量的数据库。它解决的核心问题是：**在海量向量中快速找到与查询向量最相似的 Top-K 个结果**。

**现实例子**：传统数据库像字典——按拼音/偏旁精确查找。向量数据库像一个智能图书管理员——你描述"想看一本关于太空探险的科幻小说"，它能找到语义最接近的书，即使书名里没有"太空"这个词。

## 二、核心概念

### 2.1 相似度计算方式

| 方式 | 公式直觉 | 适用场景 |
|---|---|---|
| 余弦相似度 | 两个向量夹角越小越相似 | 最常用，不受向量长度影响 |
| 欧氏距离（L2） | 两个向量之间的直线距离 | 距离越小越相似 |
| 点积（内积） | 归一化后等价于余弦相似度 | 向量已归一化时使用，计算更快 |

你项目中 Embedding 做了归一化（`normalize_embeddings=True`），所以余弦相似度和点积等价。

### 2.2 暴力搜索 vs 近似最近邻（ANN）

**暴力搜索**：查询向量和每个文档向量逐一计算距离，100% 准确但极慢。1000 万条数据每次查询要算 1000 万次。

**近似最近邻（ANN）**：牺牲少量精度换取巨大的速度提升。主流算法包括：

- **HNSW**（Hierarchical Navigable Small World）
- **IVF**（Inverted File Index）
- **PQ**（Product Quantization）

### 2.3 HNSW 算法原理

HNSW 是目前最主流的 ANN 算法，Chroma 底层就使用它。

**直觉理解**：想象一个多层的社交网络：
- 最顶层：只有少数"超级节点"，彼此相连，覆盖范围广
- 中间层：节点更多，连接更密，覆盖范围中等
- 最底层：所有节点都在，连接最密，覆盖范围最精确

搜索时从顶层开始，快速定位到大致区域，然后逐层下沉，越来越精确：

```
第 3 层（稀疏）：A ——————— B ——————— C
                              ↓
第 2 层（中等）：A — D — B — E — C
                          ↓
第 1 层（稠密）：A-D-F-B-G-E-H-C
                        ↓
                    找到最近邻！
```

**关键参数**：
- `M`：每个节点的最大连接数，越大精度越高但内存越大
- `ef_construction`：构建索引时的搜索宽度，越大索引质量越好但构建越慢
- `ef_search`：查询时的搜索宽度，越大精度越高但查询越慢

## 三、主流向量数据库对比

### 3.1 总览

| 数据库 | 类型 | 适用规模 | 部署方式 | 特点 |
|---|---|---|---|---|
| **Chroma** | 嵌入式 | <100 万向量 | 本地/嵌入进程 | 零配置，开发友好 |
| **Milvus** | 分布式 | 亿级向量 | 自托管/云 | 高性能，企业级 |
| **Pinecone** | 全托管 SaaS | 任意规模 | 云服务 | 零运维，按量付费 |
| **Qdrant** | 独立服务 | 千万级 | 自托管/云 | Rust 编写，高性能 |
| **pgvector** | PostgreSQL 扩展 | <500 万向量 | 复用现有 PG | 无需新增基础设施 |
| **Weaviate** | 独立服务 | 千万级 | 自托管/云 | 内置混合搜索 |
| **FAISS** | 库（非数据库） | 任意规模 | 嵌入进程 | Meta 出品，纯索引库 |

### 3.2 Chroma（你项目在用）

```python
from langchain_community.vectorstores import Chroma

vectorstore = Chroma.from_documents(
    documents=chunks,
    embedding=embeddings,
    collection_name="knowledge_base",
    persist_directory="./chroma_db",
)
```

**优点**：
- 零配置，`pip install chromadb` 即可使用
- 嵌入式运行，无需启动额外服务
- 支持持久化到磁盘
- 与 LangChain 深度集成
- 适合开发、测试和中小规模生产

**局限**：
- 单机运行，不支持分布式
- 大规模数据（>100 万向量）性能下降
- 不支持高并发场景

**适用场景**：学习项目、原型验证、中小规模知识库（你当前的场景完全合适）

### 3.3 Milvus（生产环境推荐）

**优点**：
- 支持分布式部署，可扩展到亿级向量
- 支持多种索引类型（HNSW、IVF、PQ 等）
- 支持混合搜索（向量 + 标量过滤）
- 有云服务版本（Zilliz Cloud）

**局限**：
- 部署复杂，依赖 etcd、MinIO 等组件
- 运维成本高
- 学习曲线陡峭

**适用场景**：大规模生产环境、高并发、需要分布式的企业级应用

### 3.4 Pinecone（全托管方案）

**优点**：
- 完全托管，零运维
- 自动扩缩容
- 内置混合搜索和元数据过滤

**局限**：
- 数据存在第三方云上，有隐私顾虑
- 成本随规模增长较快
- 供应商锁定

**适用场景**：不想管基础设施、数据不敏感、快速上线

### 3.5 pgvector（复用 PostgreSQL）

**优点**：
- 复用现有 PostgreSQL，无需新增基础设施
- 支持 SQL 查询 + 向量搜索混合
- 事务支持（ACID）

**局限**：
- 大规模向量检索性能不如专用向量数据库
- 索引类型有限

**适用场景**：已有 PostgreSQL、数据量不大、想减少基础设施复杂度

## 四、选型决策树

```
你的向量数量是多少？
├── < 100 万 → 数据是否敏感？
│   ├── 是 → Chroma（本地）或 pgvector（复用 PG）
│   └── 否 → Chroma（简单）或 Pinecone（省事）
├── 100 万 ~ 1000 万 → 是否有运维能力？
│   ├── 是 → Qdrant 或 Milvus
│   └── 否 → Pinecone
└── > 1000 万 → Milvus（自托管）或 Pinecone/Zilliz（托管）
```

## 五、向量数据库的关键操作

### 5.1 索引构建

```python
# Chroma：from_documents 一步完成向量化 + 存储
vectorstore = Chroma.from_documents(
    documents=chunks,
    embedding=embeddings,
    persist_directory="./chroma_db",
)
```

### 5.2 相似度检索

```python
# 基本检索
docs = vectorstore.similarity_search("LangGraph 状态管理", k=5)

# 带分数的检索
docs_with_scores = vectorstore.similarity_search_with_score("LangGraph", k=5)

# 带元数据过滤的检索
docs = vectorstore.similarity_search(
    "LangGraph",
    k=5,
    filter={"source": "03-LangGraph状态图与编排引擎.md"}
)
```

### 5.3 增量更新

```python
# 添加新文档
vectorstore.add_documents(new_chunks)

# 删除文档
vectorstore.delete(ids=["doc_id_1", "doc_id_2"])
```

## 六、生产环境注意事项

| 关注点 | 建议 |
|---|---|
| 索引重建 | 知识库更新后需要重建索引，考虑增量更新策略 |
| 备份恢复 | 定期备份向量数据库文件（Chroma 的 persist_directory） |
| 监控指标 | 关注查询延迟、召回率、索引大小 |
| 容量规划 | 768 维 float32 向量 ≈ 3KB/条，100 万条 ≈ 3GB |
| 冷启动 | Embedding 模型加载需要时间，服务启动时预加载 |

## 七、从 Chroma 迁移到生产数据库

当你的知识库规模增长到 Chroma 无法满足时，迁移路径：

1. **Chroma → Milvus**：适合自托管、大规模场景
2. **Chroma → Pinecone**：适合想要零运维的场景
3. **Chroma → pgvector**：适合已有 PostgreSQL 基础设施

由于你项目使用 LangChain 的 `VectorStoreRetriever` 抽象，迁移时只需替换 vectorstore 实例，检索逻辑无需改动。
