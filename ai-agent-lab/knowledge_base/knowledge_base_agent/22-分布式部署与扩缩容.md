# 分布式部署与扩缩容

> 适用场景：Agent 系统从单机部署扩展到集群部署，应对高并发和高可用需求
> 最后更新：2026 年 4 月

---

## 一、什么时候需要分布式部署

单机部署的瓶颈：

| 瓶颈 | 表现 | 触发条件 |
|---|---|---|
| CPU | Embedding 推理、Rerank 推理变慢 | 并发 > 50 |
| 内存 | Embedding 模型 + 向量索引占满内存 | 知识库 > 100 万文档 |
| 并发 | 请求排队，响应延迟飙升 | 同时在线用户 > 100 |
| 可用性 | 单点故障导致全部不可用 | 任何时候 |

**判断标准**：如果你的 Agent 需要 99.9% 可用性、支持 100+ 并发、或者知识库规模超过百万级，就需要考虑分布式部署。

---

## 二、部署架构演进

### 2.1 阶段一：单机部署（你当前的阶段）

```
用户 → FastAPI（单进程）→ Agent → LLM API
                          ↓
                    Chroma（本地文件）
                    SQLite（本地文件）
```

适用：开发、测试、小规模生产（< 50 并发）

### 2.2 阶段二：单机多 Worker

```
用户 → Nginx → FastAPI Worker 1 ─┐
              FastAPI Worker 2 ─┤→ Agent → LLM API
              FastAPI Worker 3 ─┘
                                  ↓
                            Chroma（共享目录）
                            SQLite → PostgreSQL
```

```bash
# 多 Worker 启动
uvicorn api:app --host 0.0.0.0 --port 8000 --workers 4

# 或使用 gunicorn
gunicorn api:app -w 4 -k uvicorn.workers.UvicornWorker
```

**关键变更**：
- SQLite → PostgreSQL（SQLite 不支持多进程并发写入）
- Checkpointer 改用 `PostgresSaver`

适用：中等规模（50-200 并发）

### 2.3 阶段三：多机集群

```
用户 → 负载均衡器 → 机器 A（FastAPI Workers）─┐
                    机器 B（FastAPI Workers）─┤→ LLM API
                    机器 C（FastAPI Workers）─┘
                              ↓
                    PostgreSQL（共享状态）
                    Milvus（共享向量库）
                    Redis（共享缓存）
```

**关键变更**：
- Chroma → Milvus（支持分布式）
- 引入 Redis 做缓存和会话管理
- 所有状态存储外部化（不依赖本地文件）

适用：大规模（200+ 并发）

## 三、有状态服务的挑战

Agent 是有状态的（对话历史、Checkpoint），这给分布式部署带来特殊挑战。

### 3.1 问题：会话亲和性

用户 A 的第一轮对话在机器 1 处理，第二轮可能被负载均衡器分配到机器 2。如果状态存在本地，机器 2 找不到对话历史。

### 3.2 解决方案

**方案一：外部化状态存储（推荐）**

所有状态存储在共享数据库中，任何机器都能访问：

```python
from langgraph.checkpoint.postgres import PostgresSaver

# 所有 Worker 共享同一个 PostgreSQL
checkpointer = PostgresSaver.from_conn_string(
    "postgresql://user:pass@shared-db:5432/agent"
)
```

**方案二：会话粘滞（Sticky Session）**

负载均衡器把同一用户的请求始终路由到同一台机器：

```nginx
# Nginx 配置 - 基于 cookie 的会话粘滞
upstream agent_backend {
    ip_hash;  # 基于 IP 的粘滞
    server 192.168.1.10:8000;
    server 192.168.1.11:8000;
    server 192.168.1.12:8000;
}
```

**推荐方案一**：外部化状态更可靠，机器故障时用户可以无缝切换到其他机器。

## 四、Kubernetes 部署

### 4.1 Deployment 配置

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: agent-api
  labels:
    app: agent-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: agent-api
  template:
    metadata:
      labels:
        app: agent-api
    spec:
      containers:
      - name: agent-api
        image: your-registry/agent-api:v1.0
        ports:
        - containerPort: 8000
        env:
        - name: DATABASE_URL
          valueFrom:
            secretKeyRef:
              name: agent-secrets
              key: database-url
        - name: OPENAI_API_KEY
          valueFrom:
            secretKeyRef:
              name: agent-secrets
              key: openai-api-key
        resources:
          requests:
            memory: "1Gi"
            cpu: "500m"
          limits:
            memory: "2Gi"
            cpu: "1000m"
        livenessProbe:
          httpGet:
            path: /health
            port: 8000
          initialDelaySeconds: 60  # Embedding 模型加载需要时间
          periodSeconds: 30
        readinessProbe:
          httpGet:
            path: /health
            port: 8000
          initialDelaySeconds: 30
          periodSeconds: 10
```

### 4.2 自动扩缩容（HPA）

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: agent-api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: agent-api
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 80
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60   # 扩容等待 1 分钟
      policies:
      - type: Pods
        value: 2
        periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 300  # 缩容等待 5 分钟
      policies:
      - type: Pods
        value: 1
        periodSeconds: 120
```

### 4.3 Service 和 Ingress

```yaml
apiVersion: v1
kind: Service
metadata:
  name: agent-api-svc
spec:
  selector:
    app: agent-api
  ports:
  - port: 80
    targetPort: 8000
  type: ClusterIP
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: agent-api-ingress
  annotations:
    nginx.ingress.kubernetes.io/proxy-read-timeout: "300"  # SSE 需要长超时
    nginx.ingress.kubernetes.io/proxy-send-timeout: "300"
spec:
  rules:
  - host: agent.your-company.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: agent-api-svc
            port:
              number: 80
```

## 五、Embedding 模型部署策略

Embedding 模型是 CPU/内存密集型的，在分布式环境中有几种部署方式：

| 方式 | 说明 | 适用场景 |
|---|---|---|
| 每个 Worker 内嵌 | 每个 FastAPI Worker 加载一份模型 | 小规模，简单 |
| 独立推理服务 | Embedding 模型作为独立微服务 | 中大规模，模型共享 |
| GPU 推理服务 | 用 Triton/vLLM 部署到 GPU | 大规模，低延迟 |

```python
# 方式二：Embedding 作为独立服务
import httpx

class RemoteEmbeddings:
    """调用远程 Embedding 服务"""

    def __init__(self, base_url: str):
        self.base_url = base_url
        self.client = httpx.AsyncClient()

    async def embed_query(self, text: str) -> list[float]:
        response = await self.client.post(
            f"{self.base_url}/embed",
            json={"text": text}
        )
        return response.json()["embedding"]
```

## 六、Docker Compose 部署示例

适合中等规模的快速部署：

```yaml
version: '3.8'

services:
  agent-api:
    build: .
    ports:
      - "8000:8000"
    environment:
      - DATABASE_URL=postgresql://agent:password@postgres:5432/agent_db
      - REDIS_URL=redis://redis:6379
      - OPENAI_API_KEY=${OPENAI_API_KEY}
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
    deploy:
      replicas: 3
      resources:
        limits:
          cpus: '2'
          memory: 2G
    restart: unless-stopped

  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: agent
      POSTGRES_PASSWORD: password
      POSTGRES_DB: agent_db
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U agent"]
      interval: 10s
      timeout: 5s
      retries: 5

  redis:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s

  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf
    depends_on:
      - agent-api

volumes:
  pgdata:
```

## 七、扩缩容注意事项

| 注意点 | 说明 |
|---|---|
| 冷启动时间 | Embedding 模型加载需要 10-30 秒，readinessProbe 要设足够的初始延迟 |
| 连接池 | 多 Worker 共享数据库时注意连接池大小配置 |
| SSE 长连接 | 流式输出需要长连接，负载均衡器超时要设够长 |
| 缩容风险 | 缩容时正在处理的请求可能被中断，需要优雅关闭 |
| 状态一致性 | 确保所有 Worker 使用同一个外部状态存储 |
